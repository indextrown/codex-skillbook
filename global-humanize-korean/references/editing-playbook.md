# 한국어 윤문 플레이북

## 목차

1. 진단 방법
2. 장르별 보존선

5. 과윤문 방지

## 1. 진단 방법

문장을 고치기 전에 글 전체를 읽고 지배 패턴 3~6개만 고른다. 진단은 다음 형식으로 짧게 정리하면 충분하다.

```text
- 장르·독자: 기술 블로그 / 면접관
- 말투: 합쇼체
- 보존 요소: 수치, 코드, 이력서 인용문, 링크, 이미지 위치
- 지배 패턴: 추상 주어, 같은 결말 반복, 문두 접속사, 형식명사
- 강도: 기본
```

개별 표현을 세는 것보다 글을 지배하는 습관을 찾는다. 예를 들어 `이를 통해` 한 건보다 모든 문단이 `문제 제시 → 세 가지 나열 → 의미가 크다`로 닫히는 구조가 더 큰 문제다.

## 2. 장르별 보존선

### 기술 블로그

- 기술명, API, 코드, 파일명과 버전은 보존한다.
- 문제, 선택, 구현, 검증, 결과의 인과를 분명하게 만든다.
- 전문 용어를 모두 쉬운 말로 바꾸지 않는다. 처음 등장할 때만 짧게 설명한다.
- 작성자가 실제로 한 행동을 주어로 둔다. `구조가 제공한다`보다 `빌드 스크립트가 프레임워크를 묶는다`가 낫다.
- 수치를 강조하려고 범위를 넓히지 않는다. `공통 화면 구현에서 약 2배`를 `전체 생산성 2배`로 바꾸면 안 된다.

### 이력서와 경력기술서

- 문장을 짧게 하되 문제·행동·결과 가운데 하나를 없애지 않는다.
- 성과 수치와 역할 범위를 그대로 둔다.
- `주도적으로`, `혁신적인`, `성공적으로` 같은 자기평가보다 실제 행동을 쓴다.
- 원문에 없는 리더십, 협업 인원, 비용 절감 수치를 만들지 않는다.

### 보고서와 공지

- 합쇼체나 한다체를 그대로 유지한다.
- 정책상 필요한 완곡 표현과 조건문은 남긴다.
- 제목, 표, 번호 목록은 정보 구조이므로 장식 목록과 구분한다.
- 친근하게 만들겠다고 `~해요`, 반문, 감탄을 넣지 않는다.

### 학술·법률 문서

- 제목의 단계, 번호, 각주 위치·개수·정의, 직접 인용, 참고문헌을 보존한다.
- 개념어를 쉬운 말로 바꾸다가 의미 범위를 좁히지 않는다.
- 문체의 격식을 낮추지 않는다.
- 한 문장이 길어도 법적·논리적 조건이 결합되어 있다면 함부로 나누지 않는다.

### 개인 블로그와 구어체

- `~했어요`, `~거든요`, 감탄, 반문처럼 필자의 목소리가 드러나는 부분을 살린다.
- 문장을 격식체로 높이지 않는다.
- 가짜 경험이나 `솔직히 말하면` 같은 친근함을 새로 넣지 않는다.

## 3. 문장 처방

아래 예시는 방향만 보여 준다. 결과의 말투는 언제나 원문을 따른다.

### 번역투를 동사로 되돌리기

```text
전: 사용자 피드백을 통해 문제를 파악할 수 있었습니다.
후: 사용자 피드백으로 문제를 파악했습니다.
```

가능성을 말하는 문맥이라면 `할 수 있었습니다`를 무조건 지우지 않는다.

### 추상 주어를 실제 행위로 바꾸기

```text
전: 이러한 구조는 개발자에게 빠른 검증 환경을 제공합니다.
후: 개발자는 이 구조에서 새 화면을 바로 실행해 볼 수 있습니다.
```

### 형식명사로 두 번 끝내지 않기

```text
전: 중요한 점은 두 앱이 같은 코드를 사용한다는 것입니다.
후: 두 앱은 같은 코드를 사용합니다.
```

### 빈 결론을 구체적인 결과에 붙이기

```text
전: 결과적으로, 이 접근은 매우 의미가 크다고 할 수 있습니다.
후: 공통 화면의 구현 횟수가 두 번에서 한 번으로 줄었습니다.
```

후자의 사실이 원문에 없으면 새로 만들지 말고 빈 문장만 삭제한다.

### 명사화를 풀기

```text
전: 빌드 과정의 자동화를 통한 배포 효율성 향상을 달성했습니다.
후: 빌드와 배포를 자동화해 배포 시간을 줄였습니다.
```

`배포 시간을 줄였다`는 원문에 시간 감소가 명시되어 있을 때만 쓴다. 그렇지 않으면 `빌드와 배포를 자동화했습니다`로 끝낸다.

### 이중 피동 줄이기

```text
전: 해당 설정은 자동으로 적용되어집니다.
후: 해당 설정은 자동으로 적용됩니다.
```

### 완곡 표현 하나만 남기기

```text
전: 개선될 가능성이 있을 수 있을 것으로 보입니다.
후: 개선될 가능성이 있습니다.
```

### 긴 관형절 풀기

```text
전: React Native가 생성한 헤더 경로를 Swift Package가 찾지 못해 발생한 오류를 해결했습니다.
후: Swift Package는 React Native가 생성한 헤더 경로를 찾지 못했습니다. 이 오류를 해결했습니다.
```

문장을 나눴을 때 주어가 모호해지면 두 번째 문장에 구체적인 행동을 넣되, 원문에 있는 정보만 사용한다.

## 4. 문단 처방

### 한 문단에는 중심 생각 하나를 둔다

배경, 문제, 해결책, 결과가 한 문단에 몰려 있다면 의미 단위로 나눈다. 반대로 한 문장짜리 문단이 연속되면 관련 문장을 묶는다. 문단 길이를 숫자로 획일화하지 않는다.

### 그림과 설명의 읽는 순서를 맞춘다

문서가 그림을 먼저 보여 주는 형식이라면 그림 다음 문단에서 핵심을 해석한다. 본문에서 설명한 뒤 같은 내용을 캡션으로 반복하지 않는다.

### 대구를 한 번만 살린다

`전체 앱을 바꾼 것이 아니라 공통 화면만 옮겼습니다` 같은 대조는 핵심 판단을 보여 줄 때 효과가 있다. 같은 절에서 `A가 아니라 B`를 여러 번 반복하면 나머지는 직접 서술로 바꾼다.

### 목록은 정보 구조일 때 유지한다

단계, 비교 기준, 선택지, 체크리스트는 목록이 읽기 쉽다. 한 문장을 세 개의 불릿으로 포장했거나 모든 항목이 추상명사로 끝날 때만 산문으로 바꾼다.

### 접속사를 문단마다 붙이지 않는다

앞 문단의 결론과 다음 문단의 첫 문장이 자연스럽게 이어지면 `하지만`, `따라서`, `이를 통해`를 생략한다. 논리 방향이 바뀌는 지점에서는 접속사를 남긴다.

## 5. 과윤문 방지

다음은 AI 티 제거에 실패한 윤문의 전형이다.

- 구어체를 `~하였습니다`로 올려 필자의 목소리를 없앤다.
- 모든 문장을 15~25자로 잘라 리듬을 더 기계적으로 만든다.
- 접속사와 피동문을 전부 금지해 논리 관계를 흐린다.
- 원문에 없는 사례·수치·성과를 넣어 문장을 구체적으로 보이게 한다.
- 제목과 불릿을 없애 문서의 탐색성을 떨어뜨린다.
- 전문 용어를 일상어로 바꿔 정확성을 잃는다.
- `솔직히`, `사실`, `개인적으로`를 넣어 사람인 척한다.
- 자연스러운 문장까지 유의어로 교체해 필자의 표현을 지운다.

변경률은 목표가 아니라 경고 장치다. 5% 미만이어도 필요한 곳을 제대로 고쳤다면 충분하다. 30%가 넘으면 정보 누락과 말투 변화가 없는지 다시 보고, 50%가 넘으면 문서 전체 재작성에 가까우므로 원문과 문단별로 대조한다.

## 6. 검증과 전달

검증 스크립트는 다음 요소를 확인한다.

- 문자 단위 변경률
- 수치, URL, HTML 경로, 코드 블록과 인라인 코드의 보존
- 직접 인용과 각주 정의의 보존
- front matter와 제목 단계의 의도치 않은 변화
- 합쇼체·해요체·한다체의 역주행
- 원문에 없던 상투구와 `하였` 계열의 신규 삽입

스크립트가 통과해도 의미 보존은 사람이 문맥으로 확인해야 한다. 특히 인과관계, 가능성, 조건, 부정과 새로운 주장 삽입은 정규식만으로 판정할 수 없다.

결과를 전달할 때는 윤문 자체를 앞에 둔다. 긴 진단표와 패턴 개수는 사용자가 요청했을 때만 제공한다. 파일을 수정했다면 대표적인 개선점과 검증 결과만 짧게 설명한다.
