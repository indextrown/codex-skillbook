# 테크 스펙 템플릿

## 기본 형식

아래 구조를 복사한 뒤 빈 자리 표시자와 안내 문구를 실제 내용으로 바꿔요. 해당 정보가 없으면 값을 지어내지 말고 빈 문자열이나 빈 배열을 유지해요.

```markdown
---
kind: tech-spec
title: "<기능 이름>"
status: "초안"
owner: ""
reviewers: []
last_updated: "YYYY-MM-DD"
related_issue: ""
html: "./<slug>.html"
---

# <기능 이름>

## 요약

무엇을 왜 바꾸는지 2~4문장으로 설명해요. 핵심 사용자와 기대 결과가 바로 보여야 해요.

## 배경

현재 동작과 문제를 설명해요. 문제가 생기는 조건과 영향을 구체적으로 적되, 근거 없는 수치는 쓰지 않아요.

## 목표

- 이 작업이 끝났을 때 가능해야 하는 일을 적어요.
- 구현 방법이 아니라 사용자가 얻는 결과를 우선해요.

## 목표가 아닌 것

- 이번 작업에서 의도적으로 다루지 않는 범위를 적어요.
- 이후 작업으로 미룬 내용이 있으면 이유를 짧게 덧붙여요.

## 계획

사용자 흐름과 시스템 동작을 실제 실행 순서에 가깝게 설명해요. 이 섹션이 문서에서 가장 구체적이어야 해요.

필요한 경우에만 아래 하위 항목을 선택해요.

- 사용자 흐름
- 주요 동작과 상태 변화
- API 또는 이벤트
- 데이터 구조와 저장 방식
- 오류와 경계 조건
- 배포와 이전 순서

## 고려 사항

결정이 필요하거나 구현 중 반드시 확인해야 하는 내용을 적어요. 단순한 할 일 목록이나 모든 가능성을 나열한 위험 표는 만들지 않아요.

## 마일스톤

날짜가 확정되지 않았다면 날짜를 만들지 말고 단계와 완료 조건으로 적어요.

| 단계 | 완료 조건 |
| --- | --- |
| 설계 확정 | 주요 흐름과 미결 사항에 합의해요. |
| 구현 | 목표로 정한 동작을 구현하고 검증해요. |
| 배포 | 배포 뒤 핵심 동작을 확인해요. |
```

## 섹션별 판단 기준

### 요약

문서 전체를 읽지 않아도 변경 이유와 결과를 이해할 수 있게 써요. 세부 구현은 `계획`으로 보내요.

### 배경

문제의 역사보다 지금 해결해야 하는 이유를 우선해요. 관련 코드, 이슈, 지표가 확인되었다면 링크나 경로를 남겨요.

### 목표와 목표가 아닌 것

목표는 성공 상태를 설명해요. 목표가 아닌 것은 스펙이 끝없이 커지는 것을 막을 만큼만 적어요.

### 계획

리뷰어가 구현 방향과 영향 범위를 판단할 수 있을 정도로 구체화해요. 단순한 기능은 짧은 순서 설명만으로 충분해요. API 계약, 스키마, 다이어그램은 오해를 줄이는 경우에만 추가해요.

### 고려 사항

보안, 개인정보, 호환성, 성능, 운영, 접근성 가운데 실제로 관련된 것만 다뤄요. 아직 답이 없는 질문은 누가 언제 결정해야 하는지 알 수 있게 써요.

### 마일스톤

구현 일정표보다 검토 가능한 완료 단위를 보여줘요. 날짜가 사용자나 저장소 문맥에서 확인된 경우에만 날짜 열을 추가해요.

## Markdown과 HTML의 대칭 원칙

- Markdown frontmatter와 본문을 HTML 생성 입력으로 사용해요.
- HTML은 원문의 섹션 순서와 문장을 바꾸지 않아요.
- HTML 목차와 메타데이터 카드는 읽기 위한 표현이며 새 요구사항을 담지 않아요.
- `kind`와 `html`은 동기화 제어용 필드라서 HTML 본문 정보 카드에서 제외할 수 있어요.
- HTML에만 있는 설명, 결정, 예시를 추가하지 않아요.
