# 테크 스펙 템플릿

## 저장 경로

기능마다 아래 폴더를 만들고 두 파일을 함께 저장해요.

```text
docs/tech-specs/<sequence>-<feature-slug>/
├── tech-spec.md
└── tech-spec.html
```

`<sequence>`는 `001`부터 시작하는 세 자리 번호예요. 기존 폴더에서 가장 큰 번호에 1을 더해요. 기존 번호는 다시 정렬하지 않아요.

`<feature-slug>`는 기능을 설명하는 짧은 영문 kebab-case 이름으로 정해요. 첫 번째 프로젝트별 이메일 알림 설정에는 `001-project-email-notifications`를 사용해요.

## 기본 형식

아래 구조를 복사한 뒤 빈 자리 표시자와 안내 문구를 실제 내용으로 바꿔요. 해당 정보가 없으면 값을 지어내지 말고 빈 문자열이나 빈 배열을 유지해요.

```markdown
---
kind: tech-spec
title: "<기능 이름>"
status: "초안"
owner: ""
reviewers: []
last_updated: "YYYY-MM-DD"
related_issue: ""
html: "./tech-spec.html"
---

# <기능 이름>

## 요약

무엇을 왜 바꾸는지 2~4문장으로 설명해요. 핵심 사용자와 기대 결과가 바로 보여야 해요.

## 배경

현재 동작과 문제를 설명해요. 문제가 생기는 조건과 영향을 구체적으로 적되, 근거 없는 수치는 쓰지 않아요.

## 목표

- 이 작업이 끝났을 때 가능해야 하는 일을 적어요.
- 구현 방법이 아니라 사용자가 얻는 결과를 우선해요.

## 목표가 아닌 것

- 이번 작업에서 의도적으로 다루지 않는 범위를 적어요.
- 이후 작업으로 미룬 내용이 있으면 이유를 짧게 덧붙여요.

## 계획

사용자 흐름과 시스템 동작을 실제 실행 순서에 가깝게 설명해요. 이 섹션이 문서에서 가장 구체적이어야 해요.

필요한 경우에만 아래 하위 항목을 선택해요.

- 사용자 흐름
- 주요 동작과 상태 변화
- API 또는 이벤트
- 데이터 구조와 저장 방식
- 오류와 경계 조건
- 배포와 이전 순서

## 고려 사항

결정이 필요하거나 구현 중 반드시 확인해야 하는 내용을 적어요. 단순한 할 일 목록이나 모든 가능성을 나열한 위험 표는 만들지 않아요.

## 진행 체크리스트

진행 순서가 보이도록 변경 단위와 검증 항목을 체크리스트로 적어요. 완료하지 않은 항목은 `[ ]`, 확인한 항목만 `[x]`로 표시해요.

- [ ] 1. 테크 스펙 승인
  - [ ] 1-1. <구현을 막는 미결 사항을 결정해요.>
  - [ ] 1-2. <개발자가 HTML을 검토하고 현재 스펙을 승인해요.>
- [ ] 2. <첫 번째 실제 변경 단위>
  - [ ] 2-1. <바꿀 동작이나 코드를 구체적으로 적어요.>
  - [ ] 2-2. <완료를 확인할 테스트나 관찰 결과를 적어요.>
- [ ] 3. <다음 변경 단위>
  - [ ] 3-1. <바꿀 동작이나 코드를 구체적으로 적어요.>
  - [ ] 3-2. <완료를 확인할 테스트나 관찰 결과를 적어요.>
```

## 문서 상태와 승인

- 새 문서와 내용이 바뀐 문서는 `status: "초안"`이에요.
- 개발자가 현재 내용을 명시적으로 승인한 뒤에만 `status: "승인"`으로 바꿔요.
- 승인 후 내용이 바뀌면 `초안`으로 되돌리고 다시 검토받아요.
- 체크 상태만 바뀌고 요구사항·설계·완료 조건이 그대로라면 승인 상태를 유지해요.
- 상태 변경도 Markdown에서만 하고 HTML을 다시 생성해요. HTML의 상태는 Markdown과 같아야 해요.
- 스펙 승인은 기능 구현 요청을 대신하지 않아요.

## 섹션별 판단 기준

### 요약

문서 전체를 읽지 않아도 변경 이유와 결과를 이해할 수 있게 써요. 세부 구현은 `계획`으로 보내요.

### 배경

문제의 역사보다 지금 해결해야 하는 이유를 우선해요. 관련 코드, 이슈, 지표가 확인되었다면 링크나 경로를 남겨요.

### 목표와 목표가 아닌 것

목표는 성공 상태를 설명해요. 목표가 아닌 것은 스펙이 끝없이 커지는 것을 막을 만큼만 적어요.

### 계획

리뷰어가 구현 방향과 영향 범위를 판단할 수 있을 정도로 구체화해요. 단순한 기능은 짧은 순서 설명만으로 충분해요. API 계약, 스키마, 다이어그램은 오해를 줄이는 경우에만 추가해요.

### 고려 사항

보안, 개인정보, 호환성, 성능, 운영, 접근성 가운데 실제로 관련된 것만 다뤄요. 아직 답이 없는 질문은 누가 언제 결정해야 하는지 알 수 있게 써요.

### 진행 체크리스트

구현 일정표보다 실제 변경 순서와 검토 가능한 완료 단위를 보여줘요. 기능이 크면 단계를 더 나누고, 단순하면 억지로 늘리지 않아요. `설정 구현`, `테스트 통과`만 적는 대신 `프로젝트 A의 설정을 바꿔도 B의 값은 유지돼요`처럼 변경 대상과 판정 기준을 함께 적어요. 확인한 코드 경로·모듈·테스트가 있으면 사용하고, 없는 이름은 지어내지 않아요. 하위 항목이 모두 끝난 뒤 상위 단계를 완료로 표시해요. 확인되지 않은 날짜나 진행 상태는 만들지 않아요. 체크 상태는 Markdown에서만 바꾸고 HTML을 다시 생성해요.

다음은 가상의 프로젝트별 이메일 알림 기능을 기준으로 구체성을 보여주는 예시예요. 실제 스펙에서는 사용자 요구사항과 저장소에서 확인한 코드에 맞게 다시 써요.

```markdown
- [ ] 1. 발송 기준 확정과 스펙 승인
  - [ ] 1-1. 기존 메일 전송 경로와 실패 처리 방식을 확인해요.
  - [ ] 1-2. 전송 실패 시 재시도 대상과 중단 기준을 결정해요.
  - [ ] 1-3. 개발자가 HTML에서 수신 대상과 중복 기준을 검토하고 스펙을 승인해요.
- [ ] 2. 프로젝트별 알림 설정 저장
  - [ ] 2-1. 새 프로젝트를 만든 뒤 알림 설정을 조회하면 꺼짐이에요.
  - [ ] 2-2. 프로젝트 A의 설정을 바꿔도 프로젝트 B의 값은 그대로인 테스트가 통과해요.
- [ ] 3. 설정 변경 권한 연결
  - [ ] 3-1. 관리자가 설정을 바꾸고 다시 조회하면 변경한 값이 보여요.
  - [ ] 3-2. 일반 구성원의 변경 요청은 거부되고 저장된 값도 바뀌지 않아요.
- [ ] 4. 작업 완료 전환 감지
  - [ ] 4-1. 작업이 미완료에서 완료로 바뀔 때만 알림 예약 흐름을 시작해요.
  - [ ] 4-2. 해당 프로젝트의 알림이 꺼져 있으면 예약 건수가 0건이에요.
- [ ] 5. 이메일 수신 대상 판별
  - [ ] 5-1. 해당 프로젝트의 활성 구성원 중 작업 완료자를 제외해요.
  - [ ] 5-2. 완료자와 비활성 구성원에게 예약된 이메일이 0건인지 검증해요.
- [ ] 6. 이메일 예약과 중복 방지
  - [ ] 6-1. 한 번의 완료 전환에서 수신 대상자마다 이메일을 한 통씩 예약해요.
  - [ ] 6-2. 같은 완료 전환을 다시 처리해도 대상자별 예약 건수가 늘지 않아요.
- [ ] 7. 전송 실패와 전체 시나리오 검증
  - [ ] 7-1. 메일 전송에 실패해도 작업의 완료 상태를 유지해요.
  - [ ] 7-2. 확정한 재시도 기준에 맞춰 실패 상황을 검증해요.
  - [ ] 7-3. 알림 켜짐·꺼짐, 권한, 수신 대상, 중복 방지 테스트가 모두 통과해요.
```

## Markdown과 HTML의 대칭 원칙

- Markdown frontmatter와 본문을 HTML 생성 입력으로 사용해요.
- HTML은 원문의 섹션 순서와 문장을 바꾸지 않아요.
- HTML 목차와 메타데이터 카드는 읽기 위한 표현이며 새 요구사항을 담지 않아요.
- HTML 진행 체크리스트의 체크박스와 완료 수는 Markdown 체크 상태에서만 만들어요. HTML 체크박스는 읽기 전용이에요.
- `kind`와 `html`은 동기화 제어용 필드라서 HTML 본문 정보 카드에서 제외할 수 있어요.
- HTML에만 있는 설명, 결정, 예시를 추가하지 않아요.

## 구조를 정한 근거

이 템플릿은 뱅크샐러드의 `Summary`, `Background`, `Goals`, `Non-Goals`, `Plan`, `Other Considerations`, `Milestones` 구성을 기본으로 삼아요. 마지막 섹션은 단계별 완료 상태를 보여주므로 `진행 체크리스트`라고 불러요. AB180과 Lyft의 사례에서 강조한 구현 전 맥락 공유와 리뷰 가능한 설계 문서 원칙을 함께 반영해요.
