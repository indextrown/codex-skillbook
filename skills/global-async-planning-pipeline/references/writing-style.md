# 공통 서술 원칙

Researcher, Planner, Reviewer 결과는 모두 이 원칙을 따른다. 역할마다 다루는 정보는 다르지만, 독자는 같은 문서 안에서 말투와 용어가 일관되기를 기대한다.

## 말투와 용어

- 스킬 내부 지침과 결과는 기본적으로 `-다.` 체로 쓴다. 같은 문단에서 `-요.` 체와 섞지 않는다.
- 역할명과 판정값은 `Researcher`, `Planner`, `Reviewer`, `Ready`, `Revise`, `Blocked`로 통일한다.
- `확인됨`, `추정`, `미확인`은 근거 상태를 나타낼 때만 쓴다. 같은 뜻의 다른 표현을 섞지 않는다.
- 코드, 명령어, 파일 경로, API 이름, 수치, 날짜, 인용문은 원문을 보존한다.
- 외부 근거를 사용했다면 출처와 조사 시점을 남기고, 출처가 직접 말하는 사실과 그에 따른 추정을 나눈다.

## 문장 작성 원칙

- 한 문장에는 하나의 판단이나 행동만 담는다.
- 누가 무엇을 확인하거나 바꾸는지 드러낸다. `검토가 필요하다`보다 `Reviewer가 호환성 계획을 확인한다`처럼 쓴다.
- `수행한다`, `진행한다`, `제공한다`처럼 뜻이 넓은 동사보다 실제 행동을 쓴다.
- `적절히`, `가능하면`, `필요시`처럼 기준 없는 완곡 표현을 피한다. 조건이 있으면 조건을 먼저 적는다.
- 근거가 없는 과장, 빈 결론, 메타 문장을 넣지 않는다. `중요하다`고만 쓰지 말고 어떤 위험이나 결정에 영향을 주는지 적는다.
- 불확실성이 결과의 일부라면 `추정`, `미확인`, `Blocked`로 남긴다. 확정된 사실처럼 바꾸지 않는다.

## Markdown 작성 원칙

- 역할별 문서에 정한 제목 단계와 산출물 템플릿을 유지한다.
- 비교, 상태, 우선순위처럼 열의 의미가 분명할 때만 표를 쓴다. 절차와 독립된 조건은 목록으로 정리한다.
- 장식용 강조, 이모지, 불필요한 인용문을 넣지 않는다.
- 제목은 문서의 역할이 드러나게 짧게 쓴다. 본문은 제목을 다시 설명하지 않고 필요한 기준부터 적는다.

## 최종 점검

1. 사실, 추정, 미확인 사항이 섞이지 않았는가?
2. 역할명과 판정값, 핵심 용어가 문서 전체에서 같은가?
3. 조건, 위험, 다음 행동이 바로 이해되는가?
4. 코드와 경로, 수치, 표와 목록의 구조가 바뀌지 않았는가?
5. 더 자연스럽게 고치려다 정보나 판단 기준을 빼지 않았는가?
