# Global App Store Release

## 목적

릴리즈 범위의 PR·커밋에서 사용자에게 보이는 변경사항만 골라 App Store 업데이트 문구로 작성한다. 한국어를 기준으로 필요한 현지화 문구와 App Review 메모를 함께 갱신하되, 확인하지 않은 변경이나 프로젝트 내부 정보를 사용자 문구에 넣지 않는다. 작성과 검증이 끝나면 항상 사용자의 선택을 받아, 원할 때만 Fastlane으로 메타데이터를 반영한다.

## 릴리즈 범위 정하기

1. 저장소 루트에서 현재 브랜치와 작업 트리를 확인하고, 관련 없는 로컬 변경은 보존한다.
2. 사용자가 PR·커밋 범위를 지정했으면 그 범위를 사용한다. 지정하지 않았으면 마지막 출시 태그 또는 GitHub Release와 이번 출시 대상 커밋·브랜치를 비교한다. 시작점이나 종료점이 모호하면 파일을 수정하기 전에 사용자에게 확인한다.
3. 범위 안의 병합 PR마다 번호, 제목, 본문, 라벨, 병합 시각, 변경 파일, 커밋을 수집한다. GitHub 정보를 읽을 수 없으면 로컬 커밋과 diff를 확인한다. 라벨은 분류를 돕는 자료일 뿐, 사용자에게 보이는 변경의 근거가 아니다.
4. 관련 diff를 읽고 기능, 사용자가 체감하는 UI·UX 개선, 직접적인 버그 수정만 포함한다. 리팩터링, 의존성, CI, 테스트, 관리 도구, 내부 구현은 사용자 경험에 미치는 효과가 확인될 때만 포함한다.
5. 작성 전 PR·커밋 범위와 포함·제외한 변경을 짧게 정리한다. PR 제목만으로 변경사항을 추측하지 않는다.

## 릴리즈 노트 작성

기존 App Store 메타데이터 파일이 있으면 먼저 읽는다. 지원 언어, 제목, 불릿, 말투는 기존 형식을 우선한다. 메타데이터가 없거나 새로 내려받아야 하면 사용자의 승인 범위 안에서 저장소의 배포 도구로 가져온다.

- 한국어, 일본어, 미국 영어 등 기존에 지원하는 모든 릴리즈 노트를 같은 변경 범위로 갱신한다. 파일이나 언어를 새로 추가해야 하면 먼저 사용자에게 확인한다.
- 형식이 없을 때는 `■`로 시작하는 카테고리 제목 아래에 `- ` 불릿을 사용하고, 의미 있는 변경을 한 개에서 네 개로 압축한다.
- 한국어를 먼저 자연스러운 사용자 언어로 확정한다. 일본어는 정중한 완료형(`追加しました`, `改善しました`), 영어는 과거형(`Added`, `Improved`, `Fixed`)처럼 각 언어에 자연스러운 문장으로 옮긴다. 단어 단위로 직역하지 않는다.
- PR 번호, 브랜치, 내부 모듈·데이터 모델·서비스, 빌드 도구, 확인되지 않은 수치나 약속은 쓰지 않는다.
- 근거 없는 안정성·성능 개선 문구를 덧붙이지 않는다. 사용자에게 변화가 없는 배포라면 사실대로 짧게 알리거나, 문구가 필요한지 사용자에게 확인한다.

## App Review 메모 갱신

심사 메모 파일이 존재하거나 사용자가 갱신을 요청했을 때만 이 단계를 진행한다.

1. 로그인 방법, 테스트 계정, 지원 연락처처럼 기존 심사 정보는 인증 흐름이나 공식 정보가 바뀐 근거가 있을 때만 수정한다. 누락된 테스트 정보는 만들어 내지 말고 사용자에게 요청한다.
2. 업데이트 내용 섹션에는 확정한 릴리즈 노트의 사용자 변경만 반영한다. 한국어와 영어를 함께 제공하는 형식이면 두 언어의 의미를 일치시킨다.
3. 기존 제목, 인사말, 서명, 언어 순서와 서식을 보존한다. 앱명·팀명 같은 프로젝트 고유 값은 사용자가 명시적으로 변경을 요청하지 않는 한 건드리지 않는다.

## 검증과 제출 선택

1. 수정한 파일이 UTF-8, 비어 있지 않음, 마지막 줄바꿈을 만족하는지 확인한다.
2. 한국어·일본어·미국 영어 릴리즈 노트와 한·영 심사 메모가 모두 있는 일반적인 Fastlane 구조라면 아래 검증기를 실행한다.

   ```bash
   python3 skills/global-app-store-release/scripts/validate_metadata.py \
     --metadata-root fastlane/metadata
   ```

3. 다른 언어 구성이나 디렉터리 구조라면 기존 형식과 변경 범위가 일치하는지 직접 다시 읽고, 자동 검증이 적용되지 않은 이유를 보고한다.
4. 메타데이터 작성과 검증이 끝난 뒤, 항상 아래 질문을 한다. 검증에 실패했으면 먼저 실패를 해결하고 질문하지 않는다.

   ```text
   작성 후 바로 제출하시겠습니까?
   ```

5. 사용자가 명시적으로 `yes`, `예`, `네`처럼 긍정하면 아래 질문을 추가로 한다. 모호한 답변은 긍정으로 해석하지 않는다.

   ```text
   버전을 몇으로 하시겠습니까? 예: 1.1.2
   ```

6. 숫자와 점으로만 이루어진 버전(`1.1.2` 등)을 받은 경우에만, 한 번 더 해당 버전을 보고한 뒤 아래 명령을 실행한다. 사용자 입력을 검증 없이 shell 명령에 넣지 않는다.

   ```bash
   bundle exec fastlane deliver \
     --metadata_path fastlane/metadata \
     --app_version <확인한-버전> \
     --skip_binary_upload true \
     --skip_screenshots true \
     --submit_for_review false \
     --force true
   ```

   이 명령은 바이너리와 스크린샷을 올리지 않고 메타데이터를 App Store Connect에 반영한다. `--submit_for_review false`이므로 심사 요청은 하지 않는다. 실행 결과와 실패 원인을 그대로 보고하고, 실패 시 임의로 재시도하거나 다른 배포 명령을 실행하지 않는다.

7. 사용자가 `no`, `아니`, `아니요`처럼 부정하거나 제출 여부를 답하지 않으면, 기존처럼 로컬 메타데이터 작성·검증·보고만 수행한다. 원격 반영 명령은 실행하지 않는다.
8. 사용한 PR·커밋 범위, 포함한 사용자 변경, 수정 파일, 검증 결과, 제출 여부, Git 추적 여부를 보고한다. 메타데이터가 `.gitignore`에 있으면 diff에 보이지 않을 수 있음을 분명히 알린다.

## 금지 사항

- 출시 경계가 불분명한데 임의의 변경을 포함하지 않는다.
- 근거 없는 기능, 안정성, 성능, 보안 개선을 약속하지 않는다.
- 비밀번호, 토큰, 테스트 계정 같은 민감 정보를 출력하거나 새로 만들지 않는다.
- 기존에 없는 언어, 메타데이터 파일, 심사 정보를 사용자 확인 없이 생성하지 않는다.
- 사용자의 명시적 긍정과 유효한 버전 입력 없이 Fastlane 반영 명령을 실행하지 않는다.
