# Global Planning Pipeline

## 목적

구현 전에 Researcher, Planner, Reviewer 관점을 순서대로 적용해 작업 방향을 정리한다. 이 스킬은 기본적으로 파일을 수정하지 않고 계획, 근거, 리스크, 검증 방법만 제시한다.

## 사용할 컨텍스트

이 스킬을 사용할 때는 현재 저장소 또는 작업 디렉터리 기준으로 아래 자료를 가능한 범위에서 읽고 적용한다.

1. `AGENTS.md` 또는 상위/하위 디렉터리의 적용 가능한 에이전트 지침
2. 프로젝트의 아키텍처/설계/운영 문서
   - 예: `Docs/architecture.md`, `docs/architecture.md`, `ARCHITECTURE.md`, `README.md`
3. 프로젝트에 존재하는 계획/리서치/리뷰 프롬프트
   - 예: `.codex/prompts/researcher.md`, `.codex/prompts/planner.md`, `.codex/prompts/reviewer.md`
4. 요청과 직접 관련된 코드, 테스트, 설정, 문서

문서나 프롬프트 파일이 없거나 읽을 수 없으면 파일을 생성하지 말고, 누락된 경로를 사용자에게 알린 뒤 현재 확인 가능한 정보로만 계획을 작성한다.

## 적용 조건

아래와 같은 요청에 사용한다.

- "계획 세워줘"
- "기능 방향성을 제시해줘"
- "구현 방향을 먼저 잡아줘"
- "버그를 고치기 전에 접근 방법을 정리해줘"
- "리팩터링 방향을 제안해줘"
- "구현하지 말고 계획만 세워줘"
- "먼저 검토해줘"

사용자가 "바로 구현해", "진행해", "수정해"처럼 이미 구현 승인을 명시한 경우에는 이 스킬로 계획만 반복하지 않는다. 다만 현재 프로젝트의 `AGENTS.md`나 상위 지침에 plan-first 승인 규칙이 있으면 그 규칙을 계속 따른다.

## 워크플로우

1. 현재 대화와 프로젝트 지침에서 구현 전 승인, 금지 파일, 테스트, 문서화 규칙을 확인한다.
2. 관련 문서와 프롬프트가 있으면 읽고, 없으면 일반적인 Researcher/Planner/Reviewer 관점으로 진행한다.
3. Researcher 관점으로 요청의 실제 문제, 관련 코드/문서, 제약 조건, 확인된 사실과 추정을 분리해 정리한다.
4. Planner 관점으로 추천 접근, 변경 범위, 단계별 실행 순서, 검증 방법, 문서 업데이트 필요 여부를 정리한다.
5. Reviewer 관점으로 리스크, 누락된 테스트, 범위 이탈 가능성, 호환성/보안/성능/운영 영향, 롤백 또는 대안 필요성을 검토한다.
6. 최종 추천 방향과 다음 단계를 요약한다.
7. 사용자가 계획만 요청했거나 승인이 필요한 상황이면 파일 생성, 수정, 삭제 없이 응답을 마친다.

## 출력 형식

아래 형식을 기본으로 사용한다.

```text
## Researcher 관점

## Planner 관점

## Reviewer 관점

## 최종 추천 방향
```

필요한 경우 마지막에 아래 문장을 포함한다.

```text
위 계획으로 진행해도 될까요? 승인 전까지 파일은 수정하지 않겠습니다.
```

## 금지 사항

- 사용자 승인 없이 파일을 생성, 수정, 삭제하지 않는다.
- `.env`, 인증키, 토큰, 비밀번호, 개인 정보, 배포 서명 파일처럼 민감한 파일을 열람하거나 출력하지 않는다.
- API 계약, DTO, public interface/protocol, DI 구조, 모듈 의존성, 빌드 설정 변경을 가볍게 제안하지 않는다.
- 코드 생성, 의존성 설치, 프로젝트 재생성, 마이그레이션처럼 파일을 만들거나 대량 변경할 수 있는 명령을 승인 없이 실행하지 않는다.
- 구현 단계의 세부 코드 변경을 확정 사실처럼 말하지 않는다.
- 코드 변경으로 기준 문서, 운영 문서, README, 아키텍처 문서가 달라져야 하는데도 문서 영향 여부를 생략하지 않는다.
- 확인하지 않은 내용을 프로젝트 사실처럼 단정하지 않는다.
